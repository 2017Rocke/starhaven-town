# 星栖小镇发布

## 权威来源与范围

先定位用户指定的星栖小镇仓库并核实远端。以该仓库的 `.agents/skills/starhaven-release/SKILL.md` 为权威入口，完整操作步骤、资产文件名和当前工作流行为统一读取 [docs/RELEASING.md](../../../docs/RELEASING.md)。不要在技能中维护第二份命令手册。

同名本地安装副本只用于发现技能。由副本触发时，先找到当前仓库并读取它的权威技能与 `docs/RELEASING.md`；文中的仓库路径以仓库根目录为准，不从安装目录解析。规则更新先改仓库源，再刷新安装副本。无法找到目标仓库时，不猜测远端或发布目标。

## 授权

从用户当前请求和已有会话确定操作范围。用户已明确授权发布时，继续完成该范围所需的推送、构建、发布和核验，不因进入本技能或进入下一阶段重复确认。仅要求准备、审查、封装或安装技能，不代表授权推送、创建远端标签或公开 Release；技能本身不授予这些权限。

当前请求确有发布目的、但缺少必要授权时，先完成已授权的本地准备、检查与可审阅结果，再就具体待执行的外部动作请求授权；仅要求封装技能或明确暂不发布时，完成相应本地工作即可，不追加发布确认。新的发布目标、超出原范围的外部操作或无法安全解决的权限阻断，说明实际原因后再停下；不要把等待等同于同意。

## 必须维持的发布约束

1. **保留工作与存档。** 先记录当前分支、未提交改动、远端和远端提交。同步远端后保留其他人的提交，必要时使用独立工作树整合并重新验证；不为发布覆盖未提交内容、强制重置分支或清理个人数据。安装与升级验收使用临时数据；个人数据库、账号、配置、日志和本地交接不进入公开产物。
2. **锁定同一版本和提交。** `VERSION`、`docs/UPDATE_<version>.md`、`CHANGELOG.md` 与发布说明保持一致。先完成手册要求的检查，再从指向该已验证提交的不可变版本标签构建与发布。检查远端 tag 实际解析到的 commit SHA；不能把移动中的分支、旧工作流或旧 `dist` 文件当作该标签的产物。
3. **用证据说明结果。** 核对该提交的 Checks、两种 macOS 架构和 Windows x64 构建及安装验收的实际运行结果、run ID 和 SHA。`windows-2022` 的通过只能证明该环境的结果，不能声称 Windows 10 `17763.379` 已通过实机完整验收；签名、公证和其他未完成项同样按实际证据表述。
4. **失败恢复不改写已发布历史。** 先定位失败原因并按手册修复。源码变化使用新提交与新版本标签；已公开版本的修复同时递增版本。只有同一不可变标签、无需改源码且不会替换已公开产物时，才安全重试失败工作流。禁止强推移动公开标签、删除重建版本掩盖失败或无差别 `--clobber`。遇到同名资产，先核对归属与校验和；不一致时停止覆盖并说明冲突。
5. **发布后再核验交付。** 核对远端 tag SHA、Release 对应标签与工作流提交一致，并确认 10 个必需资产齐全：两个 macOS DMG、Windows 安装器与便携包、公开源码包，以及各自的 5 个 SHA-256 文件。按手册从 Release 重新下载并核验文件名、版本及散列；上传成功或附件数量正确都不能代替下载校验。
6. **留下可接续的事实。** 将版本、commit/tag SHA、CI/构建 run、Release 地址、10 个资产的下载校验及未验收事项记录到本地 `build/release-<version>-verification.json`，同时更新维护者已有本地交接摘要。区分已公开、仍为草稿、构建失败和待用户操作；没有验证完成的发布不得报告为完成。

按实际任务只执行所需阶段：发布准备可以止于可审阅候选；已授权发布应持续到发布后核验和本地交接完成。每次修复后重跑受影响的检查和手册要求的发布门禁，再继续剩余工作。
